statmodels7

The pieces every statistical modelling package rebuilds from scratch, written once as objects you can actually reuse — carrying every derivative up to fourth order, exactly.

The problem

Open almost any R package that fits statistical models and you will find the same things written again: a handful of distributions, a handful of link functions. Not as objects — as internal helper functions, a switch on a character string, a list of closures private to the package that owns them.

So they cannot be reused. You cannot hand a link function to another package, ask a distribution for its third derivative, or add a new one without editing somebody else's source. And because each package writes only what it happens to need, what you get is almost always the density and the score, sometimes the Hessian, and nothing beyond.

Why should a Gamma be re-implemented in every package that uses one? These are fixed mathematical objects. They can be written once, correctly, with everything a modelling routine could want already computed — and then everybody builds on top.

The same is true of the optimiser. Almost every package that fits a model carries its own, written inside the function that needs it: a loop, a while (!converged), a tolerance compared against whatever quantity the author had to hand. The stopping rule — which decides what the whole thing means by finished — ends up a number nobody outside can see, let alone change.

The book

Infrastructure is only worth building on if it can be checked, so the mathematics behind the toolkit is written out in The statmodels7 Framework — a book, generated from the same source tree as the packages, in which every formula the code implements is derived from the definitions with the intermediate steps left in: the link functions and their derivatives to fourth order, the likelihood theory, the Bartlett identities, the change of scale, and the operations that build new distributions from old ones — and, in the chapter on optimizers7, Zoutendijk's theorem, the BFGS update proved symmetric positive definite, and the bundle subproblem's dual derived from its Lagrangian.

The packages

linkfunctions7

A link is an object, not a string. Fourteen of them, each carrying exact derivatives to fourth order in both directions, and a diagnostic that proves them right.

distributions7

Fourteen distributions carrying closed-form score, information and third and fourth derivatives — with respect to the parameters, the response, and the unconstrained scale.

optimizers7

Eleven algorithms as objects, and a stopping rule that is an object too — so what a run means by finished is something you set, not something buried three levels down. Box constraints are removed by reparameterisation rather than enforced.

modelterms7planned

Terms that go into a model formula — smooths, segments, jumps, penalised bases — each defining its own design and derivatives.

basis7planned

Basis expansions: B-splines, P-splines, and the machinery to build new ones.

penalties7planned

Ridge, lasso, group lasso and the rest, as objects a fitting routine can interrogate.

statmodels7planned

The package that assembles the others into models: every parameter modelled, not just the mean; optimisers you choose; frequentist or Bayesian.

What you get that you usually don't

The derivatives are the point. A modelling routine wants the score to take a step, the information for standard errors, and the third and fourth derivatives for higher-order corrections, bias adjustment or saddlepoint work. Those higher orders are almost never available, so they get approximated by differencing, or the method that needs them does not get written.

Here they are computed in closed form, in C++, for every distribution — and not only with respect to the parameters. Also with respect to the response, and with respect to the unconstrained parameters behind each link, which is the scale an optimiser actually works on. Where a closed form genuinely does not exist, what replaces it is a documented approximation, not a silence.

# everything below is exact, none of it is a finite difference
d <- gamma_distrib()
distrib_gradient(d, y, theta)                   # score
distrib_expected_hessian(d, y, theta)           # information
distrib_deriv4(d, y, theta)                     # fourth order
distrib_gradient(d, y, theta, scale = "link")   # w.r.t. eta

Built to be extended

A toolkit that only works for the fourteen distributions it ships with would have solved nothing. Everything dispatches on S7 generics, so your own distribution is a subclass and one method — the density. The distribution function, the quantile function, the sampler and every derivative then follow from numerical fallbacks, and each one you later derive in closed form silently takes over.

The same holds for link functions, and will hold for model terms, bases and penalties as those arrive. If you write a component, it works with everything already here — and everything already here works with yours.

check_distrib() and check_link() exist for that reason: they put your component through the same numerical validation the shipped ones face, so a derivative you got wrong is caught before it reaches a model.

Conventions

  • Every package is a plural noun followed by 7 — the S7 object system, and the plural of what it provides.
  • Derivatives are exact and analytical wherever a closed form exists, and numerically validated where one does not.
  • Nothing is private. What the packages use internally is exported, documented and available to you.
