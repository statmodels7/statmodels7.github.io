statmodels7

The components every statistical modelling package rewrites internally, written once as reusable objects that carry every derivative up to fourth order, exactly.

The problem

Almost every R package that fits statistical models contains its own private copy of the same components: a handful of distributions and a handful of link functions. They are written not as objects but as internal helper functions, a switch on a character string, a list of closures private to the package that owns them.

Written that way, they cannot be reused. A link function cannot be handed to another package, a distribution cannot be asked for its third derivative, and adding a new one means editing somebody else's source. Because each package writes only what it needs, what is available is almost always the density and the score, sometimes the Hessian, and nothing beyond.

A Gamma is a fixed mathematical object. It can be written once, correctly, with everything a modelling routine could want already computed, and every package can then build on the same implementation. That is what this toolkit provides.

The same argument applies to the optimiser. Almost every package that fits a model carries its own, written inside the function that needs it: a loop, a while (!converged), a tolerance compared against whatever quantity the author had to hand. The stopping rule, which decides what the whole procedure means by finished, ends up as a number that nothing outside the package can read or change.

The book

The mathematics behind the toolkit is written out in The statmodels7 Framework, a book generated from the same source tree as the packages. It presents every formula the code implements: the link functions and their derivatives to fourth order, the likelihood theory and the Bartlett identities, the change of scale, and the operations that build new distributions from existing ones. The chapter on optimisation covers the methods themselves, from the Wolfe conditions and Zoutendijk's theorem to the BFGS update and the bundle method.

The packages

linkfunctions7

Sixteen link classes, each carrying exact derivatives to fourth order in both directions, with numerical fallbacks for user-defined links and a diagnostic that verifies every order.

distributions7

Fourteen univariate distributions and two multivariate ones, carrying closed-form score, information and third and fourth derivatives — with respect to the parameters, the response, and the unconstrained scale.

optimizers7

Eleven algorithms as objects, with the stopping rule an object as well, chosen and combined by the caller instead of buried in the loop. Box constraints are removed by reparameterisation rather than enforced.

basis7

Bases that can be evaluated, differentiated to any order, integrated, and asked for their inner products: the Gram matrix a roughness penalty integrates, exact rather than approximated on a grid.

covstructs7

Constrained matrix parameters as objects: covariance and precision structures that map an unconstrained vector to a matrix, with exact derivatives, log-determinants and solves. Rank-deficient precisions included, because that is what a penalty is.

modelterms7planned

Terms that go into a model formula — smooths, segments, jumps, penalised bases — each defining its own design and derivatives.

penalties7planned

Ridge, lasso, group lasso and the rest, as objects a fitting routine can interrogate.

statmodels7planned

The package that assembles the others into models: every parameter modelled rather than just the mean, pluggable optimisers, and frequentist or Bayesian estimation.

The derivatives

A modelling routine needs the score to take a step, the information for standard errors, and the third and fourth derivatives for higher-order corrections, bias adjustment or saddlepoint approximations. The higher orders are almost never available in existing packages, so they are approximated by differencing, or the method that needs them is not written at all.

Here they are computed in closed form, in C++, for every distribution, with respect to the parameters, to the response, and to the unconstrained parameters behind each link, which is the scale an optimiser works on. Where a closed form does not exist, a documented numerical approximation takes its place.

# everything below is exact, none of it is a finite difference
d <- gamma_distrib()
distrib_gradient(d, y, theta)                   # score
distrib_expected_hessian(d, y, theta)           # information
distrib_deriv4(d, y, theta)                     # fourth order
distrib_gradient(d, y, theta, scale = "link")   # w.r.t. eta

Matrix parameters

A parameter is not always a number. A covariance matrix must be positive definite, a correlation matrix has ones on its diagonal, a spline penalty is positive semidefinite and singular by construction. A link function cannot express any of these, because it acts on one number at a time and produces a diagonal Jacobian, while changing one free value of a matrix parametrisation changes an entire row and column.

covstructs7 supplies the missing object: a map from an unconstrained vector to a constrained matrix, exact to second order, together with the log-determinant and the solves a likelihood asks for. Its consumers are the multivariate distributions below and, when it arrives, penalties7.

# a covariance, with every free value ranging over R
s <- log_cholesky(3)
struct_matrix(s, eta)          # the matrix
struct_dmatrix(s, eta)         # dM/deta, one per free value
struct_logdet(s, eta)          # log|M|, linear in eta here

# a second-difference penalty: singular, and that is the point
d <- diff(diag(10), differences = 2)
p <- scaled_struct(crossprod(d))
p@rank                         # 8 of 10
struct_dlogdet(p, eta)         # the rank, at any scale

Vectors, not just numbers

A multivariate distribution is the same object with a matrix parameter. Its mean contributes one scalar per coordinate and the covariance contributes the free values of whatever structure parametrises it, so the parameter vector stays a list of numbers and every generic in the package indexes it as it always did — including the derivatives, the validator and the fitting routine.

d <- mvgaussian_distrib(3)
d@params                 # the mean, then the structure

fit <- fit_distrib(d, y) # the same fit_distrib()
plot(fit)                # contours against the data

# heavy-tailed: nu is estimated with everything else
mvstudent_t_distrib(3)

Where a fit begins is part of the model, not of the implementation, so a family is asked for its own starting value. One that knows an estimator returns it: a multivariate gaussian starts at the sample mean and covariance, which for an unstructured matrix is the answer, and the fit confirms it in a single iteration.

A gaussian may be parametrised by its precision instead of its covariance, which is a different model whenever the structure is not closed under inversion, and the constructor takes either side; the parameter names say which of the two, so a printed table is never ambiguous. The Student t keeps its scale matrix and its covariance apart, so it can be described and fitted at degrees of freedom where the second moment does not exist.

A Cholesky coordinate is not something anyone reads, and it is not what a fit prints. What it prints is the quantities that are read: standard deviations and correlations, each with a standard error carried across by the delta method and an interval built on a scale it cannot escape from — the log scale for a standard deviation, Fisher's z for a correlation. A precision parametrisation adds the conditional variances and partial correlations, which are what it describes directly.

mv_summary(fit)
#            Estimate  Std. Error     2.5%    97.5%
# sd_v1        1.0687      0.0182   1.0337   1.1048
# sd_v2        0.8956      0.0156   0.8655   0.9268
# cor_v1_v2    0.4254      0.0197   0.3860   0.4634

Built to be extended

A toolkit that only worked for the fourteen distributions it ships with would have solved nothing. Everything dispatches on S7 generics, so a user-defined distribution is a subclass with one method, the density. The distribution function, the quantile function, the sampler and every derivative then follow from numerical fallbacks, and each closed form derived later takes over as soon as it is registered as a method.

The same holds for link functions, and will hold for model terms, bases and penalties as those arrive. A user-written component works with everything already here, and everything already here works with it.

check_distrib() and check_link() exist for that reason: they put a user-written component through the same numerical validation the shipped ones face, so a wrong derivative is caught before it reaches a model.

Conventions

  • Every package name ends in 7 — the S7 object system everything is built on.
  • Derivatives are exact and analytical wherever a closed form exists, and numerically validated where one does not.
  • Nothing is private. What the packages use internally is exported and documented.
